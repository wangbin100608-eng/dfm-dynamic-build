# 原生 x86_64 测试环境报告（任务3）

- 实例：`redroid-x86-test`（独立，端口 5556，未触碰生产实例）
- 启动命令见 `可复现部署配置.md`

## 3.1 环境

```
docker run -itd --privileged --name redroid-x86-test \
  -v /root/redroid-x86-test-data:/data -p 5556:5555 \
  redroid/redroid:11.0.0-latest \
  androidboot.redroid_width=1080 androidboot.redroid_height=1920 androidboot.redroid_dpi=480
```

- 挂载检查：只有 `/root/redroid-x86-test-data → /data`，**无自定义转译器 bind**（与生产实例不同）。
- 转译器：镜像原生 `/system/lib64/libndk_translation.so`（2021-10-06，1,654,288 字节）。

## 3.2 图形栈（CPU 软件渲染）

```
ro.hardware.egl = swiftshader
ro.opengles.version = 196610 (OpenGL ES 3.2)
ro.hardware.vulkan = pastel
```

- EGL/GL 库：`libEGL.so / libGLESv1_CM.so / libGLESv2.so / libGLESv3.so / libvulkan.so` + 对应 `libndk_translation_proxy_lib*`
- 图形服务：`surfaceflinger` (pid 81)、`android.hardware.graphics.composer@2.1-service` (pid 67) 均正常
- **EGL 初始化正常（满足已知环境），但见任务2/4：这不代表 APP 兼容性正常**

## 3.3 ABI 基准

```
ro.product.cpu.abilist = x86_64,x86,arm64-v8a,armeabi-v7a,armeabi
```

关键：**即使"不安装 ARM 转译组件"，redroid 镜像仍自带 libndk_translation.so 并声明 arm64 支持**——无法通过"不安装"禁用转译。

## 3.4 目标 APP 安装

```
docker cp dfm-official-1.201.37119.49.apk redroid-x86-test:/data/local/tmp/dfm.apk
pm install -r /data/local/tmp/dfm.apk → Success
```

## 3.5-3.7 启动与资源记录

| 时间点 | CPU | 内存 | 进程 | 前台 |
|---|---|---|---|---|
| 启动前 | 1.70% | 791MiB | — | — |
| SplashActivity 后 12s | **377.33%** | 2.583GiB | pid 1921 | PermissionActivity |
| 进入 GameActivity 后 | 0.74% | 2.72GiB | pid 2083 | PermissionActivity（未推进） |

- native 库加载：初期 14 个 SDK so（maps 中确认），后期 UE4 主库按需加载（生产实例观测到 RSS 1GB 峰值）。
- EGL/OpenGL ES/SurfaceFlinger：正常（无错误）。
- **启动时间**：Splash→PermissionActivity 约 12 秒（含大量 JIT 预热）；进入 GameActivity 后未能完成初始化（见任务4）。

## 基准结论

原生 x86_64 平台能力（Docker/Binder/ashmem/SwiftShader/EGL）全部就绪；但目标 APP 是纯 arm64，必须走 Native Bridge，而 Native Bridge 存在任务4 所述问题。平台层无瓶颈，瓶颈在 ARM 转译层。
